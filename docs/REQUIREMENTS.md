# Falsify — 开发需求文档

版本 1.0 · 状态 DRAFT · 目标 Build with Gemini XPRIZE

## 1. 文档信息

| 项 | 内容 |
|---|---|
| 产品名称 | Falsify |
| 一句话 | Pay agents to falsify claims. What survives is worth the settlement. |
| 类别 | 专业服务普及 / 小企业服务 |
| 目标交付 | 公开仓库、可运行产品、3 分钟视频、500–1000 词说明、真实交易证据 |

## 2. 产品定义

Falsify 是一个面向可验证 AI 工作的去信任结算协议。客户发布一个**论断**（对代码、
数据或系统的声明）、一套已提交的验收测试和一笔 USDC 赏金。对抗 Agent 竞争性地生成
**反例**去证伪该论断。只有当反例被确定性证明"使已提交测试失败"时，赏金才释放。
无效反例得 0，并在链上记录为虚假贡献声明。

## 3. 问题

1. 事后无法可靠判断一段内容是否由 AI 生成，还是有人类深度引导。
2. AI Agent 会"乱说"，产出没有可验证证据的论断。
3. 现有 Agent 支付协议按调用、按任务或固定比例付费，没有一个奖励"说得对"。

### 3.1 为什么做（背景）

三件事同时在发生：

1. AI 产出代码、报告和数据的速度，已经远超人类验证它们的速度。
2. 事后无法判断一条论断到底有没有真实人类判断参与，还是纯模型生成。
3. 现有 Agent 支付协议只奖励"被调用"，从不奖励"说对"。

结果是：Agent 经济正在被大量无人能验证的论断淹没，而没有任何结算原语奖励正确。
Falsify 就是填补这个空缺的原语——**付钱让 Agent 去推翻论断，幸存本身即证明**。

### 3.2 核心问题

一句话：**信任没有验证。**

- 一条 AI 论断（"这合约是安全的"、"这数据是对的"）制造便宜、验证昂贵。
- 事后 AI 检测不可靠，且可被对抗绕过。
- 按次付费和固定分账都无法区分"正确"与"幻觉"。

## 4. 目标用户

- 即将上线智能合约 / 核心模块，测试全绿但心里没底的独立开发者与小团队。
- 需要"上线前找人主动打破它"的软件/协议团队。
- 后续：需要可信第三方验证的审计、保险、数据与专业服务方。

## 5. 核心机制

```text
客户发布论断 + 验收测试 + USDC 赏金
  -> 对抗 Agent 生成反例
  -> 确定性验证器（Cloud Build）运行已提交测试
  -> 测试失败：反例有效 -> 赏金付给发现者
  -> 测试通过：反例无效 -> 发现者得 0，声誉被标记
  -> ERC-8004 记录身份与声誉；x402 作为 HTTP 支付轨道
```

### 5.1 双路径（两条都保留）

| 论断类型 | 反例生成器 | Gemini 角色 |
|---|---|---|
| 正确性 / 数据 | Gemini | 生成反例输入 |
| 安全 / 漏洞 | 确定性工具（fuzzer / Slither / 攻击夹具） | 只解释，不生成 exploit |

安全类反例刻意不让 Gemini 生成漏洞利用代码；由确定性工具生成，Gemini 仅把失败的
测试翻译成人话。两条路径共用同一个确定性验证器，放款决策永不依赖 LLM。

## 6. 用户流程

### 6.1 客户（发布方）

1. 提交论断（自然语言）+ 验收测试（可运行）+ 赏金金额 + 截止时间。
2. 系统把论断结构化并托管赏金。
3. 收到"反例有效"通知后查看证据，修复问题。
4. 若无人证伪，支付基础费并取回未释放的赏金。

### 6.2 对手 Agent（发现方）

1. 发现公开论断。
2. 生成候选反例（攻击输入 / 破坏性参数）。
3. 提交反例，由确定性验证器判定。
4. 有效则收到赏金；无效则得 0 并被记录。

## 7. 功能需求

### FR-01 论断发布

- 客户提交：论断文本、验收测试引用、赏金金额（USDC）、截止时间。
- 系统生成 `assertionHash`，并把赏金托管。

### FR-02 反例提交

- Agent 提交反例产物（输入/攻击参数/证据）。
- 每个反例生成唯一 `counterexampleHash`，用于防重放。

### FR-03 确定性验证

- 验证器在隔离环境运行"已提交测试 + 反例"。
- 结果只能是：`FALSIFIED`（测试失败）或 `NOT_FALSIFIED`（测试通过）。
- 验证不由 LLM 决定。

### FR-04 赏金结算

- `FALSIFIED`：赏金释放给第一个有效反例的发现者。
- `NOT_FALSIFIED`：不释放，记录 `falseContributionClaim`。

### FR-05 声誉写回

- 记录：`validCounterexamples`、`falseClaimRate`、`wastedCallRate`。

### FR-06 证据与日志

- 保存：论断、反例、验证输出、付款交易、Agent 日志、Gemini 调用记录。

## 8. 非功能需求

- **安全**：验证器独立于对手 Agent；Agent 不能自评分；私钥与 API key 不进客户端。
- **确定性**：相同反例 + 相同测试得到相同判定。
- **幂等**：同一反例只结算一次。
- **可观测**：每个反例的提交、验证、付款都可追溯。
- **诚实标注**：测试网交易与主网交易必须分开标注。

## 9. MVP 边界

### 做

- 单论断 + 单套测试 + 3 个对手 Agent + 1 个确定性验证器。
- 1 笔真实主网 USDC 赏金结算。
- ERC-8004 注册 + Validation/Reputation 写回。
- 公开仓库 + 3 分钟视频 + 500–1000 词说明。

### 不做（MVP 排除）

- 多论断并发、竞价市场、人工评审、质押经济、跨链、治理。
- 事后 AI 文本检测器（不可靠，不做）。

## 10. 验收标准

- [ ] 客户能发布论断并托管 USDC。
- [ ] 对手 Agent 能提交反例。
- [ ] 确定性验证器能复现"反例使测试失败"。
- [ ] 有效反例触发赏金释放，无效反例得 0 并记录。
- [ ] 一笔真实主网 USDC 交易可点击验证。
- [ ] ERC-8004 记录身份、验证与声誉。
- [ ] 评委不看文档也能在 3 分钟内理解机制。

## 11. 成功指标

- 1 个真实客户 + 1 笔真实赏金。
- 1 个有效反例 + 1 个无效反例（正反对比）。
- 完整 Agent 日志 + Gemini 调用记录 + P&L。

## 12. 风险与应对

| 风险 | 应对 |
|---|---|
| 验证器无法确定性复现失败 | 6 小时内验证；失败则缩小到单一定义清晰的检查 |
| 拿不到愿意设赏金的客户 | 降级为演示 + 诚实披露 0 收入 |
| 反例"有效性"边界争议 | 只认"已提交测试失败与否"这一客观判据 |

## 13. 状态标记

- `[已实现并通过测试]`：结算合约（ETH/USDC + ERC-8004 身份门控与声誉写回 + x402
  支付证明字段 + 防重放 + 退款）、双路径反例脚本。
- `[尚未验证]`：Circle、GCP 集成、真实主网 USDC、Coinbase x402 验证器。
- `[48小时内可以完成]`：第 9 节 MVP 范围的剩余部分。
- `[需要外部用户配合]`：真实赏金客户、真实 USDC。
- `[未来规划，不属于MVP]`：多论断、质押、跨链、治理。

## 14. 商业价值

- **谁付钱**：即将上线合约 / 模块 / 数据管线、想在发布前被"主动攻击"的团队。
- **为什么付**：一条经受过付费证伪的论断，比一条没人攻击过的论断更可信。这与安全审计、
  漏洞赏金是同一个需求，但放款由机器判定，而非声誉判定。
- **收入**：每笔结算赏金抽 15% 平台费；持续对抗测试是后续扩展路径。
- **诚实说明**：收入只有在"真实、无关联的客户托管并结算了真实赏金"时才算数。

## 15. 黑客松硬性规定对照

| 硬性规定 | Falsify 如何满足 |
|---|---|
| 部署应用至少调用一次 Gemini API | Gemini 生成反例并解释为何测试失败 |
| 至少使用一项 Google Cloud 产品 | Cloud Run、Cloud Build、Firestore |
| 展示可运行产品 | 可部署的证伪闭环：发布 -> 攻击 -> 验证 -> 结算 |
| Agent 执行有价值操作或决策 | 对抗 Agent 生成攻击；确定性验证器决定放款 |
| 提供真实用户证据 | 一个托管真实赏金的客户 |
| 如实申报收入支出 | 成功费、平台费、P&L 均记录 |
| Agent 执行日志、API 记录、截图 | Firestore 证据、Gemini 调用日志、Cloud Build 输出 |
| 代码仓库、<=3 分钟视频、500-1000 词说明 | 随提交一并交付 |
| 披露复用模板框架 | ERC-8004（Draft）、x402 V2、OpenZeppelin、Foundry |
